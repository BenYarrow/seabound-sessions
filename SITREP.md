- **🐛 Climate averages corrected (partial months)** — the `/destinations` wind/temp curves were inflated. `DestinationController` averages `weather_records` across years with **equal weight per row**, which is only valid if every row is a full month — but the fetch window started mid-month, nothing pruned, and rows that fall out of the rolling window are never re-fetched, so stubs **froze permanently**. Langebaan's July 2023 row held **4 days** (28–31 July) yet carried 25% of typical July, inflating it to 11.6 kts; every spot had 4 July rows, and Karpathos/Le Morne had five contaminated months each. **Why the ranking was fine but the charts weren't:** the two layers have deliberately opposite rules — `spot_sailable_days` is coverage-normalised so partial months are correct there, while `weather_records` is equally weighted so they are poison. The fix solved for one layer had never been applied to the other. Now: window snaps to a month boundary; a row is written only when the month is both fully **received** (day count vs calendar length) and fully **elapsed**; and a spot's rows are **replaced** per fetch, which makes it self-healing and is why there is no data migration. Collect-then-write means a failed fetch can never blank a spot. Also fixed: days with no readings for a metric were contributing a phantom `0.0`. **The elapsed gate exists because Open-Meteo forecast-fills the current day** — found only because verification ran against real data and reported BLOCKED rather than forcing a pass. Verified on Postgres: every spot now has exactly 3 rows per month (36 = 36 complete months), July 2023 went from a 4-day stub @15.0 kts to a full 31 days @10.6, typical July 11.6 → 11.1. Suite **263**. **Owner:** run `php artisan weather:fetch` on Cloud — self-healing, but only on the next fetch. See [2026-07-31-climate-partial-months](docs/history/2026-07-31-climate-partial-months.md).

- **Sailable-days ranking (destinations redesign)** — `/destinations` now ranks spots by the *typical* number of "sailable days" in a chosen month for a user-set minimum wind (kts/mph/kph), reordering the actual cards live, client-side. A "sailable day" = ≥2 hours ≥ minimum within the 9am–7pm window, encoded as the day's 2nd-highest hour and stored in a new daily `spot_sailable_days` layer (populated by `WeatherFetcher` alongside the monthly `weather_records`). The ranking metric is a **GUST + sustained-floor BLEND** — a day counts iff `qualifying_gust_kts ≥ X` **AND** `qualifying_wind_kts ≥ 0.6·X` — reached through two post-launch corrections against lived knowledge: (1) sustained→gust after Karpathos's June read ~1 sailable day when the meltemi blows almost daily (Open-Meteo's sustained 10m under-reads thermal/venturi spots; gusts track felt wind); (2) gust→blend after pure-gust let spiky storm-prone Karpathos (gust/sustained ≈ 2.1) outrank steady Langebaan (≈ 1.3) even midwinter — the sustained floor rejects gusty-not-steady frontal-storm days, steady spots unaffected (fixed December; January narrows but still leans Karpathos, the residual being temperature, deliberately deferred). The typical-days figure is a coverage-normalised rate (robust to the rolling 3-year window's partial boundary months). A new URL-synced filter bar (Month / Group by continent·country·global / Spots / Unit / Min wind / **Min temp**) drives three layouts plus a new sailable-days-per-month bar chart and the retained typical-year wind/temp charts; on mobile the bar collapses to a ~50px tap-to-expand header. Each card now shows the month's typical air temp (`≈ 18 windy days · 11°C`) and an **opt-in Min-temp filter** (Any default / 10 / 15 / 20 / 25 °C) lets a warmth-seeker exclude cold spots — temperature is *surfaced/filterable, never gated into the ranking* (a hard gate would wrongly bury cold-water spots like Brouwersdam whose season is winter).
